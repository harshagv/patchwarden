How it works

From a free scan to a site that stays safe.

  1. 1

    Scan it from the outside.

    Enter a domain, or upload a CSV of up to 1,000 client sites. Each one gets a one-page report an owner can read: your version, your risk, what to do next. A hidden version is reported as unknown, never guessed.

  2. 2

    Approve the fix.

    Every update starts as a dry run that lists exactly what will happen. Once the owner approves, Patchwarden backs up, updates, restarts and checks the homepage, login and checkout pages.

  3. 3

    Let it keep watch.

    Protected sites are re-checked every day, and every new PHP flaw is matched the hour it is published. Flaws attackers are already using reach the owner at once; the rest arrive as a daily digest.

  4. 4

    Move what can't be patched.

    PHP 8.1 and older have no fix. Patchwarden finds the code that will break, down to the file and line, gives a fixed price, tests the move on a staging copy, and goes live only after sign-off.

It never changes a site you haven't approved.

Every change starts as a dry run, is backed up first, and puts itself back if the homepage, login or checkout stops working, with a before/after report to prove it.

Shield it at the edge first.

A change freeze, an old plugin, a migration still being planned: some sites can't take the PHP update today. A virtual patch blocks attack-shaped requests at your CDN or firewall, before they reach PHP. It buys time; it doesn't replace the update.

Trust

The owner holds the keys.

These rules are enforced in the code and covered by automated tests, not just written in a policy.

No password, ever.

Owners give an API token they create in their hosting panel, or install the plugin. Tokens are encrypted, never shown again, and revoked in one click.

Approval on the record.

Who approved, and when, is saved before anything runs. Every action lands in a tamper-evident, hash-chained audit log.

Backups you can prove.

Each backup is encrypted, checked by checksum and a restore dry-run, and deleted after 30 days. If the server stops mid-change, the site is put back from it.

Untrusted code stays in a box.

Rector, PHPStan and php -l run in a container with no network, a read-only file system and no privileges.

Nothing leaks.

Canary tests prove no credential reaches a response, report, alert, email or log. Two-step login and rate limits guard the dashboard.

No AI guessing.

The agents are deterministic checkers. A hidden version stays "unknown" until it can be checked from the inside.

Run it

Running in three steps.

Patchwarden is one web app plus PostgreSQL, packaged for Docker. It runs natively on Apple Silicon and x86.

  1. Get it, and make your secrets.

    Get the code, then write a private .env with generated values for the token key, the encryption key and the database password. It never goes into git.

    git clone https://github.com/harshagv/patchwarden.git
cd patchwarden
make env

  2. Point it at your domain.

    Set PUBLIC_BASE_URL in .env to your HTTPS address, and add SMTP if you want alerts by email. Then check the settings: in production, Patchwarden refuses to start and names any missing secret.

    make check-config

  3. Start it.

    It listens on 127.0.0.1:8000, so put it behind your HTTPS reverse proxy. Site owners download the WordPress plugin from their dashboard, already set up for your address.

    make up

Try it first, on your laptop

make dev starts Patchwarden with built-in demo websites, pretend hosting panels and a demo edge firewall, so you need no accounts and no secrets. Patch a site, watch one roll itself back, shield one at the edge, and plan a migration from PHP 7.4, all in about five minutes. The guide walks through it.

Questions

Before you ask.

Do site owners have to give you their password?

No. They create an API token in their hosting panel (cPanel or Plesk) or install the WordPress plugin. Either can be revoked at any time, and access ends on both sides.

What happens if an update breaks the site?

After every change Patchwarden checks the homepage, the login page and the checkout. If any of them fails, it restores the backup and switches PHP back on its own, then sends a before/after report.

Is a virtual patch enough on its own?

No. It blocks the request shapes that PHP remote-code-execution attacks use, which buys time. The real fix is the PHP update or the migration, and the shield comes off once that is done.

Does anything leave my server?

Patchwarden is self-hosted. It calls the public advisory feeds (NVD, php.net, CISA KEV, FIRST EPSS), the sites you scan, and the hosting panels, edge providers and alert channels you connect. Nothing else.

Does it use AI to decide what to change?

No. Every agent is a deterministic checker with tests. Where it cannot see something, it says "unknown" instead of guessing.

Is it free?

The code is open source under the MIT licence: run it yourself. If you want help running it for your clients, get in touch.
